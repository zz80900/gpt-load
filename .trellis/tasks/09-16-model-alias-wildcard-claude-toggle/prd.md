# 模型别名通配符匹配与 Claude 适配开关

## Goal

让模型别名支持通配符，使一个上游模型能接住一整类客户端模型名（典型场景：把
`claude-opus-5` / `claude-sonnet-5` 等任意 Claude 模型名统一路由到
`deepseek-flash`），并在分组模型编辑表格中提供一个「Claude 适配」滑动开关作为
该能力的开箱用法。

## 背景

现状（`internal/modelname`、`internal/state/snapshot.go`）只有两条名称归一规则：

1. 精确别名：别名与请求名逐字节相等才命中。
2. 上下文后缀归一：别名 `xxxx[1M]` 额外以基名 `xxxx` 注册，供 Claude Code 这类
   客户端先用带后缀名探到大窗口、再用基名发请求。

两者都无法表达「任意 Claude 模型名」。用户只能为每个可能出现的模型名逐个配别名，
而 Claude 客户端发来的模型名集合是不受控的。

## Requirements

### 通配符语义

- **R1** 别名中含 `*` 时按通配符处理，`*` 匹配任意长度（含空）的字符序列；别名中
  不含 `*` 时行为与今天逐字相同。
- **R2** 只支持 `*` 一种通配符，不支持 `?`、字符类、转义或正则。
- **R3** 精确优先：请求名在路由索引中有精确键时，必须**只**使用精确键的目标，
  不得与任何通配符匹配结果合并或排序。
- **R4** 通配符之间重叠时的裁决必须确定且与配置顺序无关：首个 `*` 之前的字面前缀
  更长者优先；仍相同时字面字符总数更多者优先；再相同时按字节序取小。
- **R5** 通配符与上下文后缀正交：别名 `claude-*[1m]` 既以自身注册，也以剥掉后缀的
  `claude-*` 注册（沿用既有 `RoutableModelNames` 派生规则），因此
  `claude-opus-5`、`claude-opus-5[1m]` 两种请求都能命中。
- **R6** `*` 不被特殊禁止：`*` 单独成别名时匹配该分组内所有无精确键的请求名。这是
  合法配置，其后果（未知模型名不再落 503 而是走到该上游）必须写入文档。

### Claude 适配开关

- **R7** 分组详情页的模型编辑表格中，在「别名」列与「价格状态」列之间新增一列，
  内含一个滑动开关，标题为「Claude 适配」。
- **R8** 该列**只在分组详情页**出现。批量导入页复用同一个编辑器组件，但不得渲染
  这一列，且其表格列布局必须与改动前逐字一致（不能因为新增列而跟着多出一个空轨道）。
- **R9** 开关打开：向该模型的别名追加常量别名 `claude-*[1m]`；关闭：从别名中移除
  该常量（若存在的是 `claude-*[1M]`，移除它）。开关状态由「别名中是否包含该常量」
  推导，**不新增持久化字段**。开关在分组内**互斥**：打开一个必须自动关闭该分组内
  其他所有已打开的开关，保证同一时刻只有一个模型启用；关闭某个开关只影响它自己。
  互斥由前端自动完成，用户不需要先手工关掉另一个。后端对同名模式的冲突规则（R17）
  保持不变，作为开关管不到的手输路径的兜底。
- **R10** 该常量别名不在别名输入框中展示，也不参与表格搜索的匹配文本；改由开关
  承载其状态。
- **R11** 开关打开时写入的永远是规范形态 `claude-*[1m]`（小写）。
- **R12** 隐藏不得造成数据丢失：保存时该常量必须原样写回，不能被当作「已删除的
  可见别名」丢弃。该条在导入页同样成立——即使那里不渲染开关列。
- **R13** 用户在别名输入框里手输的其他别名（含其他通配符别名，例如 `gpt-*`）仍
  照常展示、编辑、删除，不受 R10 的隐藏规则影响。

### 展示层可见性

- **R14** 通配符别名不得出现在 `/v1/models` 返回的模型列表中——模式不是可请求的
  具体模型名，列出它会让客户端把它当成真实模型。
- **R15** 通配符别名不得出现在下列任何「客户端可用名称」枚举面：
  分组选项/模型候选选择器、模型页（`/models`）的名称列表与上游关联明细、价格引用
  计数、首页仪表盘的名称聚合与客户端配置生成器、访问密钥作用域选择器，以及前端
  任何由 `client_models` 派生出的名称建议列表。
- **R16** 通配符别名仍必须出现在路由索引里并被请求命中；R14 / R15 是展示层过滤，
  不得退化成「不注册」。

### 冲突检测

- **R17** 同一分组内，两个**不同上游 ID** 配置了同一个通配符别名时，保存阶段必须报
  `MODEL_NAME_CONFLICT`，且 `conflicts[].client_model` 等于该模式字符串。这条规则
  不变；Claude 适配开关通过 R9 的互斥在到达它之前就消解掉了它最常见的触发路径，
  剩下的触发路径是用户在别名框手输重复常量，或库里已存在改动前的重复数据。
- **R18** 编译期（`validateCompileInput`）对同一情况必须拒绝发布新快照，行为与既有的
  精确名称冲突一致。
- **R19** 同一个上游 ID 的多条配置记录共用同一个通配符别名不算冲突（沿用既有规则）。
- **R20** 通配符与精确名之间不构成冲突：`claude-*` 与 `claude-opus-5` 可以共存，由
  R3 决定请求走哪条。
- **R21** 两个**不同但重叠**的模式（`claude-*` 与 `claude-sonnet-*`）可以共存，由 R4
  决定请求走哪条；不得被判为冲突。

### 文档

- **R22** 在三份 README 的模型/分组配置相关小节补充说明：别名支持 `*` 通配符、
  精确匹配优先、`*` 通配符别名不会出现在 `/v1/models` 与各类选择器中，以及
  「Claude 适配」开关等价于写入别名 `claude-*[1m]`。

## Constraints

- **C1** 不新增数据库字段、不做数据迁移。通配符别名就是普通别名，落在既有
  `aliases` JSON 数组里，用户手改配置文件也能生效。控制面读路径的
  `GroupModel.UnmarshalJSON` 使用 `DisallowUnknownFields`，新增字段会直接 500 掉分组
  列表，因此这条约束是硬性的而非偏好。
- **C2** `client_models` 仍是 `[id, ...aliases]` 的逐项展开（`state.ExternalModelNames`
  不改）——前端 `web/src/app/resources/groups.ts` 对它做逐项硬断言。模式名以字面量
  出现在 `client_models` 里，过滤只发生在消费这些名称的展示点（R15）。
- **C3** 未使用通配符的既有配置，其对外可见名称集合、路由索引、冲突判定必须逐项
  不变——现有测试套件的期望值不得因为本特性而调整。
- **C4** 别名条数上限（`maxAliasesPerModel`=10）与单名长度上限（`maxModelNameBytes`=255）
  对通配符别名同样生效，但它们**只在写路径**（`normalizeModelAliases`）强制，编译期与
  loader 不校验。本任务不改变这一现状，但方案不得依赖「已发布快照里的别名必然
  满足这两个上限」这一假设。
- **C5** 不扩展访问密钥模型白名单（`modelname.Allows`）的通配符语义。白名单描述的是
  「客户端可以用哪些名称发请求」，R14 已把模式名挡在选择器之外。已知后果并被接受：
  若用户绕过选择器手输 `claude-*` 进白名单，该项永不命中，该密钥会以
  `model_filtered` 拒绝请求。不为此新增写路径校验——那会让既有存量数据在编译期失败
  并冻结配置发布。
- **C6** 别名体自身的字符校验现状不变（今天允许控制字符）。修正它超出了本任务范围，
  但方案不得在此基础上再引入依赖「别名无控制字符」的新逻辑。
- **C7** 上游模型 ID 含 `*` 的语义不在本任务处理范围（ID 与别名走同一套「含 `*` 即
  模式」判定）；该组合的计价身份与目录匹配行为需在文档中标注为已知边界。
- **C8** 批量导入页复用 `ModelAliasEditor`，但不渲染 Claude 适配列（R8）。因此该列
  的启用与它的文案必须由同一个可选项控制，使导入页既不产生空轨道，也不必提供一份
  用不到的必填文案字段。导入页的行不会产生该常量别名，但一旦草稿里存在它（例如从
  恢复草稿载入），保存时必须原样保留（R12）。

## Non-Goals

- 不做模型名的服务端重写回显：客户端请求名原样透传并被原样回显，不因命中通配符
  而改写。
- 不支持 `?`、字符类、转义、正则或路径段匹配。
- 不为通配符提供「优先级 / 权重」配置项（优先级只由 R4 的特异性规则决定）。
- 不统一 `internal/parameteroverride` 已有的「结尾单个 `*` 即前缀匹配」方言。两套方言
  并存是有意的：前者作用于人写的参数覆盖规则，后者作用于模型别名；本任务只在
  design 中记录该差异，不修改规则语义。
- 不在「路由巡检」响应中新增「命中了哪个模式」字段。巡检页当前还要求模型名必须
  属于已配置集合（`InspectorTab.vue` 的 `validatedRequest`），因此通配符路由在管理端
  的逐请求可观测性本任务不解决，作为后续项记录。
- 不处理模型同步（`GroupModelSyncDialog`）删除后重新添加导致开关状态丢失的问题：
  该行为与今天任何别名在重加时被清空的行为一致。

## Acceptance Criteria

标注 `[手工]` 的条目需人工验证——`web/` 下没有测试运行器（`web/package.json` 无 `test`
脚本、无 vitest、仓库内 0 个前端测试文件），前端只能靠 `vue-tsc`、`eslint`、`prettier`
与浏览器实测。

### 路由

- [ ] **AC1** 配置 `{"id":"deepseek-flash","aliases":["claude-*[1m]"]}` 后，客户端请求
      `claude-opus-5`、`claude-sonnet-5`、`claude-opus-5[1m]`、`claude-*[1m]` 四种名称
      全部解析到上游 `deepseek-flash`，且 `UpstreamModelID` 等于 `deepseek-flash`。
- [ ] **AC2** 另有一个条目带精确别名 `claude-sonnet-5` 时，请求 `claude-sonnet-5`
      路由到该条目；请求 `claude-opus-5` 仍路由到 `deepseek-flash`。
- [ ] **AC3** 请求名既无精确键、又无任何通配符命中时，仍返回 503
      `no_available_candidate`；`ReasonNoRouteTarget` 的判定逻辑不变。
- [ ] **AC4** 两个模型分别配 `claude-*` 与 `claude-sonnet-*` 时，请求 `claude-sonnet-5`
      稳定命中后者；打乱配置顺序、重建快照后结果一致。
- [ ] **AC5** 无模型资源请求（`NoModelRouteKey` 路径，如 Responses retrieve/delete）
      不参与通配符匹配。

### 后端保存与冲突

- [ ] **AC6** 保存带通配符别名的分组后重新读取，`aliases` 与 `client_models` 与保存
      前逐项一致（模式名以字面量出现在 `client_models` 中）。
- [ ] **AC7** 同一分组内两个不同上游 ID 配同一通配符别名时，保存返回
      `MODEL_NAME_CONFLICT`，`conflicts[].client_model` 等于该模式字符串。
- [ ] **AC8** 同一上游 ID 的两条记录共用同一通配符别名时，保存成功。
- [ ] **AC9** 两个不同但重叠的模式（`claude-*` 与 `claude-sonnet-*`）保存成功，不被
      判为冲突。
- [ ] **AC10** 冲突导致保存失败时，不发布新快照、不改动已存模型（沿用既有失败原子性）。

### 展示层

- [ ] **AC11** `/v1/models` 的三种协议响应中都不存在任何含 `*` 的名称。
- [ ] **AC12** 分组选项接口返回的模型候选集不含任何含 `*` 的名称。
- [ ] **AC13** 模型页的名称列表、上游关联明细与 `price.reference_count` /
      `associations.length` / `client_model_count` 相互一致，且都不计入模式名。
- [ ] **AC14** 首页仪表盘的模型名称集合与客户端配置生成器不含任何含 `*` 的名称。
- [ ] **AC15** `[手工]` 分组模型编辑表格的别名输入框中看不到 `claude-*[1m]`。
- [ ] **AC16** `[手工]` 别名输入框中手输的 `gpt-*` 正常展示、可删除、保存后仍在。

### 前端开关

- [ ] **AC17** `[手工]` 对某模型打开「Claude 适配」并保存后，重新拉取该分组，开关仍为
      打开，且后端 `aliases` 数组包含 `claude-*[1m]`。
- [ ] **AC18** `[手工]` 该模型同时有可见别名 `foo`，关闭开关后保存，`aliases` 为
      `["foo"]`。
- [ ] **AC19** `[手工]` 该模型没有其他别名时，关闭开关后保存，`aliases` 为 `[]`。
- [ ] **AC20** `[手工]` 同一分组内第二个模型打开开关时，第一个模型的开关自动关闭，
      界面上任何时刻都只有一个开关处于打开状态；保存后只有第二个模型的 `aliases`
      含 `claude-*[1m]`。
- [ ] **AC25** `[手工]` 在别名框里手输 `claude-*[1m]`（开关之外的通路）造成的重复仍
      按 AC20 的旧口径处理：表格给出可定位的错误，而不是指向一个看不见的别名字符串。
- [ ] **AC21** `[手工]` 开关列位于「别名」与「价格状态」两列之间，表头顺序与列内容
      一一对应；860px 断点下卡片依次为 ID / 别名 / 开关 / 价格状态，无横向溢出。

- [ ] **AC22** `[手工]` 批量导入页的模型表格**没有** Claude 适配列，且其列布局与改动
      前逐字一致（不出现空轨道）。
- [ ] **AC23** `[手工]` 导入页的模型行保存时，若草稿里存在 `claude-*[1m]`（例如从恢复
      草稿载入），该别名被原样写回而不被丢弃。

### 回归

- [ ] **AC24** 不涉及通配符的既有测试保持原样的期望值并通过。

## Notes

- **关键不变量（本任务必须修正既有 spec）**：`.trellis/spec/backend/model-name-contract.md`
  第 3 节写「路由索引是唯一注册点：`/v1/models` 遍历索引键，因此把派生名注册进去就
  免费出现在列表里」，第 7 节又把「在查找路径加兜底」列为 Wrong。这两条对**有限可
  枚举**的后缀派生成立，对**不可枚举**的通配符不成立：客户端请求名来自一个无穷
  集合，模式无法在构建期展开成索引键。因此本任务必须同时修订该 spec——新增通配符
  名称集合的说明、精确优先规则、模式特异性裁决规则，并重写 Wrong 示例。不修订会
  让下一个人按旧契约实现出一个永不命中的通配符。
- 常量别名 `claude-*[1m]` 只在前端定义（`web/src/features/models/model-draft.ts`）。
  后端把它当作普通通配符别名处理，不需要对应的 Go 常量，因此不存在跨语言字符串
  同步问题。
- 本任务触及跨层契约 `client_models` 与模型页计数契约。两者都有前端单点硬断言
  （`groups.ts` / `models.ts`），任何一处口径不一致都会整页白屏，实现时必须按
  `design.md` 的清单逐点核对。
